# 005 — Google login (BFF), visitors, release candidates

Optional "Sign in with Google", an anonymous identity for every browser, and
merging the two on login. Code: `src/main/kotlin/de/yscord/auth/`,
`frontend/src/app/auth/`.

## Shape: BFF (backend for frontend)

```
browser ── click "Sign in" ──► GET /oauth2/authorization/google  (Spring)
        ◄── 302 to accounts.google.com?client_id=…&redirect_uri=…&state=…
        ── user picks an account at Google ──►
        ◄── 302 to <redirect_uri>?code=…&state=…
        ── GET /login/oauth2/code/google?code=… ──► Spring exchanges the code
                                                   for tokens (server to Google),
                                                   stores the session in Postgres
        ◄── 302 to / with a SESSION cookie
```

1. **The server is the OAuth client**, the browser only holds a session cookie.
   Tokens in `localStorage` (OAuth done in the SPA) are stolen by any XSS.
2. **OIDC** (OpenID Connect) on top of OAuth tells *who* logged in. Users are
   keyed by `sub`, Google's stable account id — email can change.
3. **Sessions in Postgres** (Spring Session JDBC): they survive restarts and work
   across replicas. The table schema is third-party: copied verbatim into a
   migration, `initialize-schema: never`.
4. **Login is optional:** `anyRequest().permitAll()`, the player stays public.
5. **Logout** is a POST with CSRF; `csrf.spa()` puts the token in the readable
   `XSRF-TOKEN` cookie, Angular's HttpClient sends it back as `X-XSRF-TOKEN`.
6. Edge auth (Envoy Gateway `SecurityPolicy`, oauth2-proxy, Cloudflare Access)
   fits "protect everything" (Grafana, Argo UI). Optional login + merging with
   anonymous history is application logic, so it lives in the app.

## Visitors and identity stitching

1. Every browser gets `visitor_id` (UUID, `HttpOnly`, `Secure`, `SameSite=Lax`,
   one year) on its first request; a row in `visitor`. The filter runs **before**
   Spring Security (order -110 vs -100): the OAuth callback is answered by
   Security and never reaches later filters.
2. On login the visitor is linked to the user (`visitor.user_id`): everything
   this browser did anonymously now belongs to the user, nothing is rewritten.
   Each device links its own visitor.
3. A browser already linked to someone else (shared computer) gets a **new**
   visitor for the new user: one person's history never moves to another.
4. `last_seen_at` is written at most once an hour per visitor (in-memory note),
   not on every audio range request.

## redirect_uri behind proxies

1. Google compares `redirect_uri` with the registered list **character for
   character**, twice: when sending the browser to Google and when the server
   exchanges the code. Its purpose: nobody can have the code sent elsewhere.
2. Spring derives it from the incoming request. Behind
   Cloudflare (https) → cloudflared → Envoy → app (http) it came out `http://`
   → `redirect_uri_mismatch`.
3. Trusting `X-Forwarded-Proto` (`forward-headers-strategy`) didn't help:
   **Envoy overwrites it** with its own downstream scheme (http). Verified by
   experiment, then dropped.
4. Fix: the public URL is environment config, like Grafana's `root_url` or
   GitLab's `external_url`. `APP_PUBLIC_URL` builds the redirect URI and decides
   `Secure` cookies. The host is written once, in the HTTPRoute; kustomize
   `replacements` fills it into `APP_PUBLIC_URL` when rendering.
5. Google's registered list can't be read through an API, so nothing can check
   it automatically. The app logs its redirect URI at startup, and
   `yscord-deploy/scripts/oauth-redirect-uri.sh` prints it from the released
   manifests.

## Secrets and config

```fish
read -P "client id: " cid; read -s -P "client secret: " csec
printf '{"client-id":"%s","client-secret":"%s"}' $cid $csec | docker exec -i openbao bao kv put -mount=secret yscord/google -
set -e cid csec
```

`read -s` hides the input, fish's builtin `printf` never shows up in `ps`.
ExternalSecret `google-oauth` → env `GOOGLE_CLIENT_ID/SECRET`. Local copies of
credentials live in `creds/`, ignored by git and the Docker build context.

## Release candidates

Pushes to main never deploy, so testing on the cluster needs a tag:

1. `v0.7.0-rc.1`, `rc.2`, …: built, pushed as `0.7.0-rc.N`, deployed like any
   release, but never tagged `latest`.
2. The release is **the exact commit that passed as an rc**:
   `git tag v0.7.0 v0.7.0-rc.4`.
3. Staging (later) is where candidates should go instead of production.
