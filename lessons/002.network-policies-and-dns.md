# 002 — NetworkPolicy and cluster DNS

A firewall for pods, and the DNS every pod depends on. Our policies live in
[k8s/base/network-policies.yaml](../k8s/base/network-policies.yaml).

## Why

Kubernetes networking is **flat** by default: any pod can open a connection to any
other pod, and out to anything the node can reach — including your home LAN.
We proved it: from the app pod, `yt-dlp` downloaded the FRITZ!Box admin page, and
a pod in `edge` (next to the internet-facing cloudflared) opened a connection to
Postgres.

The app's YouTube-only allowlist is one layer. NetworkPolicy is a second,
independent one at the network level (defense in depth): if the app check is ever
bypassed, the packets still don't get through.

## Who enforces it

Kubernetes only **stores** NetworkPolicy objects. The **CNI** plugin (Container
Network Interface — the module that builds the pod network) enforces them.
minikube's default CNI ignores them silently: `apply` says `created` and nothing
changes. That's why the cluster was rebuilt with `--cni=calico`
(see [001](001.cluster-migration.md)).

Always verify a policy with a real connection attempt — never trust `created`.

## The whitelist rule

1. A pod **not selected by any policy** is fully open.
2. A pod **selected by at least one policy** (for a direction: Ingress or Egress)
   only gets what the **union** of all policies selecting it allows.
3. Traffic between a pod and **its own node** is always allowed — so kubelet
   probes keep working under default-deny.

Analogy: no bouncer → everyone gets in. A bouncer with an empty guest list →
nobody gets in. Each allow-policy adds names to the list.

## The workflow

1. Record the "before": try the connections you want to block (they succeed).
2. Apply **default-deny** (empty `podSelector` + both `policyTypes`, no rules).
3. Watch what breaks; diagnose (`get` → `describe` → `logs`).
4. Add allow-policies one flow at a time.
5. Record the "after": the bad connections time out, the app works.

Our flows:

```
Envoy ──8080──► yscord ──5432──► postgres
                  ├──53──► cluster DNS (CoreDNS in kube-system)
                  └──80/443──► internet, except private ranges
```

## Syntax traps

### AND vs OR — one dash makes the difference

```yaml
# AND: pods labelled kube-dns INSIDE namespace kube-system
- to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector: { matchLabels: { k8s-app: kube-dns } }
```

```yaml
# OR: ANY pod in kube-system, OR kube-dns pods in OUR namespace
- to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
    - podSelector: { matchLabels: { k8s-app: kube-dns } }
```

Both are valid, neither errors. The second one is silently much wider.

### Selecting namespaces

Every namespace automatically carries the label
`kubernetes.io/metadata.name: <name>` — use it in `namespaceSelector`.

### ipBlock and in-cluster traffic

`ipBlock` matches IPs. Pod IPs (`10.244.x.x`) and service IPs (`10.96.x.x`) sit in
`10.0.0.0/8`, which our internet rule **excludes** on purpose. In-cluster flows
(DNS, Postgres) are allowed by **label** selectors instead, which don't care
about IPs.

Excluded ranges and why:

| Range | What lives there |
|---|---|
| `10.0.0.0/8` | private; pod and service IPs |
| `172.16.0.0/12` | private; Docker networks |
| `192.168.0.0/16` | private; home LAN, minikube node network |
| `169.254.0.0/16` | link-local; cloud metadata endpoint `169.254.169.254` |
| `100.64.0.0/10` | carrier-grade NAT |

## DNS: allow it first

Under default-deny the restarted app failed with `UnknownHostException: postgres` —
not on port 5432, but one step earlier: it couldn't look up the name. Allowing
DNS is the first rule in almost every policy set, and its absence produces the
most misleading symptoms.

### How a name becomes a pod

```
"postgres:5432"
  1. DNS (CoreDNS): postgres.yscord.svc.cluster.local → Service IP 10.96.x.x
  2. network (kube-proxy rules on the node): 10.96.x.x → a ready pod 10.244.x.x
```

1. DNS resolves **Services**, not pods. It doesn't balance or track pods.
2. The Service IP is virtual — no interface has it. Node rules rewrite it to a
   ready pod's IP (the EndpointSlice list).
3. Exception: a **headless** Service (`clusterIP: None`, our Postgres) skips step 2 —
   DNS returns pod IPs directly. StatefulSet pods also get their own names:
   `postgres-0.postgres.yscord.svc.cluster.local`.

### What the pod's resolver looks like

```fish
kubectl exec deploy/yscord -- cat /etc/resolv.conf
```

```
nameserver 10.96.0.10                         ← the kube-dns Service (CoreDNS pods)
search yscord.svc.cluster.local svc.cluster.local cluster.local fritz.box
options ndots:5
```

1. `search` is why `postgres` works from the same namespace, while another
   namespace needs `postgres.yscord`. Full form: `<service>.<namespace>.svc.cluster.local`.
2. Names outside `cluster.local` are **forwarded** by CoreDNS to the node's
   resolver (here: the FRITZ!Box). So even `youtube.com` needs the DNS rule.
3. `ndots:5`: a name with fewer than 5 dots tries every search domain first.
   `www.youtube.com` costs five lookups (`…yscord.svc.cluster.local`,
   `…svc.cluster.local`, `…cluster.local`, `…fritz.box`, then the real one).
   Harmless for us; on busy clusters it overloads DNS. Fix: a trailing dot
   (`youtube.com.`) or `dnsConfig.options` on the pod.

## Testing connections

```fish
# from the app pod, bypassing the app's own allowlist (expect a timeout)
kubectl exec deploy/yscord -- /tools/yt-dlp --simulate --socket-timeout 5 http://192.168.178.1/

# a throwaway pod in another namespace, pretending to be a compromised neighbour
kubectl run probe -n edge --rm -it --image=busybox:1.37 --restart=Never -- nc -zv -w 3 postgres.yscord 5432

# DNS from inside the namespace (allowed for all pods)
kubectl run dnstest --rm -it --image=busybox:1.37 --restart=Never -- nslookup postgres
```

`nc -z` only checks whether a TCP connection opens: `open` = reachable,
timeout = blocked by policy.

## Also learned along the way

1. During the broken default-deny rollout the old pod kept running: the new pod
   never became ready, so the rolling update never removed the old one.
2. Logs die with the pod. Once the failing pod was replaced, its
   `UnknownHostException` was gone — real clusters ship logs to a store (Loki,
   Elasticsearch).
