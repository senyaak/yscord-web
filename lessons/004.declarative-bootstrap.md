# 004 — Declarative bootstrap: deploy repo, app of apps, external secrets

A fresh cluster from one script: Argo CD installs everything else from git, and
secrets come from an external store. Repos:
[yscord-deploy](https://github.com/senyaak/yscord-deploy) (what runs),
this repo (code + the app's manifests), `~/Projects/openbao-local` (lab secret store, local only).

## Why

1. Manifests on main deployed instantly while the image only came with a tag —
   a manifest change needing a new image broke prod before its release.
2. Rebuilding a cluster meant a page of manual steps in the right order (lesson 001).
3. Secrets were created by hand per cluster, from files on the laptop.

## Deploy repo

| Path | Written by |
|---|---|
| `apps/` | humans: one `Application` per component, `root.yaml` manages them all |
| `argocd/`, `envoy-gateway/` | humans: upstream installs pinned by URL + version |
| `platform/` | humans: Gateway, EnvoyProxy, tunnel, secret store |
| `yscord/` | the release job only, one commit per release |

1. Argo CD watches **only** the deploy repo. Pushing to the app repo's main
   never reaches the cluster; a `vX.Y.Z` tag does, through the release job.
2. The release job copies the tagged commit's `k8s/base` + release overlay to
   `yscord/`, pins the image, and pushes **one commit**: manifests and image
   ship together. It writes with a **deploy key** (write access to that one repo;
   `GITHUB_TOKEN` can't write to other repos).
3. App manifests stay next to the code (they change together); platform
   lives in the deploy repo (it changes on its own schedule).
4. Without a staging environment nobody runs main's images, so CI only
   **builds** on main/PRs and **pushes** on tags.

## App of apps

```
root (apps/)        applied by hand once, manages itself and its children
  -2  argocd           Argo CD manages its own install
  -1  envoy-gateway    CRDs + controller
  -1  external-secrets Helm chart, rendered by Argo CD
   0  platform         Gateway, EnvoyProxy, cloudflared, ClusterSecretStore
   1  yscord           ExternalSecret -1, Postgres 0, migration Job 1, app 2
```

1. **Waves between Applications don't wait by default:** Argo CD doesn't assess
   an Application's health. A Lua health check in `argocd-cm` (argocd/argocd-cm.yaml)
   makes a wave wait until the previous children are really healthy.
2. **Big CRDs** need `ServerSideApply=true` (they overflow the last-applied annotation).
3. **Argo CD managing itself** can break itself with a bad commit and then can't
   roll back. Recovery: `kubectl apply -k argocd/ --server-side --force-conflicts`
   from a good commit. That's why the argocd app has `prune: false`.
4. **Deleting an Application doesn't delete its resources** without the
   `resources-finalizer.argocd.argoproj.io` finalizer: they're orphaned, root
   recreates the Application, it adopts them again. We leave the finalizer out on
   purpose: removing a component should be deliberate, not a typo in `apps/`.
5. **Helm hooks are Argo hooks:** a `helm.sh/hook: pre-install` Job (Envoy's
   certgen, with a 30 s TTL) is treated as PreSync and not diffed — no
   recreate loop. `kubectl diff` doesn't know that and shows it as missing.

## Secrets: store → ESO → Secret → pod

```
OpenBao (host)            External Secrets Operator (cluster)
 secret/yscord/postgres ──► ClusterSecretStore "secrets" ──► ExternalSecret ──► Secret ──► pod
 secret/edge/cloudflared       (AppRole login)
```

1. Pods only read Kubernetes Secrets (env, volumes). ESO is the bridge: it reads
   the store and writes Secrets. The app never knows the provider.
2. **The provider is chosen in one place**, the `ClusterSecretStore`, named
   neutrally (`secrets`). ExternalSecrets only say "key `yscord/postgres` from
   store `secrets`". Switching to a cloud secret manager changes the store only.
3. **Secret zero:** ESO's own login (AppRole `role-id` + `secret-id`) is the one
   Secret created by hand — by the bootstrap script now. In the cloud, workload
   identity (e.g. IRSA on EKS) removes even that.
4. **Adoption:** an ExternalSecret whose target Secret already exists takes it
   over (`Updated` event, `ownerReferences: ExternalSecret`). On a fresh cluster
   it's `Created`.
5. **Ownership goes one way:** delete the Secret → ESO recreates it; delete the
   ExternalSecret → the Secret is garbage-collected.
6. **Controllers converge:** an ExternalSecret applied together with its store
   logs "store not found" until the store exists, then syncs. A sync wave on the
   store only removes the noise.
7. Changing a value in the store updates the Secret within `refreshInterval`,
   but not running pods (env is read at start) and not Postgres
   (`POSTGRES_PASSWORD` only applies at first init).

### OpenBao in the lab

1. Runs in Docker on the host, so it survives cluster rebuilds. Listens on
   `127.0.0.1` for you and joins the cluster's docker network
   (`docker network connect <profile> openbao`): pods resolve container names on
   that network through CoreDNS → node DNS. Not exposed to the LAN.
2. **Sealed** after every start: data is encrypted at rest, the unseal key opens
   it (`bao operator unseal`). Production uses auto-unseal through a KMS.
3. KV v2 under `secret/`, policy `eso-read` (read-only, two paths), AppRole `eso`.
4. Secrets go in through **stdin**, never as arguments (shell history, `ps`,
   `docker events`):

```fish
kubectl get secret postgres-credentials -o json | jq '.data | map_values(@base64d)' | docker exec -i openbao bao kv put -mount=secret yscord/postgres -
docker exec -i openbao bao kv put -mount=secret edge/cloudflared credentials.json=- < ~/.cloudflared/<tunnel-id>.json
```

## Bootstrap script

`scripts/bootstrap.sh --profile <name> [--restore dump.sql]` in the deploy repo.

1. **Idempotent:** each step checks first; after a failure, fix and re-run.
2. **Preflight** stops early with the fix: missing tools, store not running /
   sealed / not logged in, secrets or AppRole missing, dump taken without
   `--clean --if-exists`, **another cluster running** (shared tunnel).
3. Then: minikube with Calico, store on the cluster network, Argo CD from
   `argocd/` (so the health check exists from the first sync), secret zero,
   root app, optional restore, wait until everything is Synced and Healthy.

### Restore while Argo CD self-heals

The app keeps the player state in memory and writes all of it every 5 s, so a
restore under a running app gets overwritten. The script:

1. waits for Postgres;
2. pauses auto-sync — **root first**, or it reverts the child's pause;
3. scales the app to 0, restores, re-applies `root.yaml` (which restores both
   sync policies; self-heal scales the app back up).

## One tunnel, many clusters

Every cluster runs the same tunnel credentials. Cloudflare treats all connectors
of a tunnel as replicas and spreads requests across them: two live clusters =
requests split between two databases (split-brain). So:

1. Only one cluster may run (preflight enforces it); migration is a
   **maintenance window**: dump → stop old → bootstrap new with `--restore` →
   verify → delete old.
2. During the window the site goes 1033 (no connector) → 404 (no route yet) →
   briefly an empty player → 503 (app stopped for the restore) → back.
3. Zero-downtime blue/green needs an entry point **outside** the clusters
   (cloud load balancer, a tunnel per cluster + DNS switch) that is switched at
   the end.

```fish
kubectl --context <old> exec postgres-0 -- sh -c 'pg_dump --clean --if-exists -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > /tmp/yscord-dump.sql
minikube stop -p <old>
~/Projects/yscord-deploy/scripts/bootstrap.sh --profile <new> --restore /tmp/yscord-dump.sql
minikube delete -p <old>
rm /tmp/yscord-dump.sql
```
