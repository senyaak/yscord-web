# 003 — Argo CD, releases and migrations

GitOps with Argo CD, a tag-driven release pipeline, and database migrations that
run as a gated step of the rollout. Diagrams: [docs/architecture.md](../docs/architecture.md).

## Why

1. Deploying with `kubectl apply` from a laptop means only the cluster knows what
   runs in it. Manual edits drift away from git.
2. CI can't push into the cluster: it's behind NAT, and handing GitHub cluster
   credentials is a bad idea anyway.
3. Migrations ran inside every app pod at startup: two replicas could race, and a
   broken migration crash-looped the app.

## GitOps, pull model

An agent **inside** the cluster pulls desired state from git and applies it.
Nothing connects into the cluster from outside, so NAT doesn't matter.

| Piece | Job |
|---|---|
| `application-controller` | compares git with the cluster, applies changes |
| `repo-server` | clones git, renders manifests (`kustomize build`) |
| `server` | UI and API |
| `Application` (CRD) | "keep this git path in sync with this namespace" |

Install (the only manual step; Argo can't install itself):

```fish
kubectl create namespace argocd
kubectl apply -n argocd --server-side --force-conflicts -f https://raw.githubusercontent.com/argoproj/argo-cd/v3.5.3/manifests/install.yaml
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d; echo
kubectl -n argocd port-forward svc/argocd-server 8443:443    # UI on https://localhost:8443, never exposed publicly
```

Our app: [k8s/argocd/yscord.yaml](../k8s/argocd/yscord.yaml).

### What Argo does and doesn't do

1. **Adoption.** Existing resources with matching names are taken over; Argo marks
   them with the `argocd.argoproj.io/tracking-id` annotation. No restart: that
   lands in metadata, not in the pod template.
2. **Diffs are textual.** `image` is a string. Changing `sha-0faae7c` to `0.1.0`
   rolls the pods even if both point to the same bytes. Only a digest
   (`image@sha256:…`) makes "same content" mean "same string".
3. **Argo reads git, kubelet pulls images.** A private repo breaks the sync
   (`ComparisonError`); a private image breaks the pod (`ImagePullBackOff`).
   Different credentials, different places.
4. **Cluster changes are seen in seconds** (watch). **Git changes are polled**
   (~3 min). The **Refresh** button re-reads git now; a webhook would need Argo
   reachable from GitHub.

### Sync policy

```yaml
syncPolicy:
  automated:
    prune: true      # delete what was removed from git (only resources Argo tracks)
    selfHeal: true   # revert manual changes in the cluster
  retry:
    limit: 1         # explicit; the implicit default is 5
```

1. Without `syncPolicy` Argo only reports drift (a camera without a guard).
2. With `selfHeal`, `kubectl scale`/`edit`/`rollout undo` are reverted within
   seconds. A rollback is a `git revert`.
3. The `Application` itself was applied by hand, so editing it in git does
   nothing until you `kubectl apply` it again. App-of-apps fixes that.
4. History lists **successful** syncs only. A failed operation keeps the
   `startedAt` of its first attempt across retries.

Pause and resume auto-sync:

```fish
kubectl -n argocd patch application yscord --type merge -p '{"spec":{"syncPolicy":null}}'
kubectl apply -f k8s/argocd/yscord.yaml
```

## Releases: tag → promote → commit → sync

```
git push main        → CI: build + test → image sha-xxxxxxx
git push tag v1.2.3  → CI release job:
                        1. tag must be on main
                        2. imagetools create: add tag 1.2.3 to sha-xxxxxxx (no rebuild)
                        3. kustomize edit set image in k8s/overlays/release
                        4. commit "Release v1.2.3 [skip ci]" to main
                     → Argo sees the commit, syncs
```

1. **Build once, promote.** The release ships the exact bytes that were tested.
   A rebuild could pull newer base layers.
2. **Deploy = commit.** One bot commit per release is the audit log and the
   rollback handle. A git tag alone can't carry the image: the image is built
   after the commit.
3. **Tags are pushed separately:** `git push origin v1.2.3`. Plain `git push`
   doesn't send them.
4. Tag only green commits; the release job fails if the image isn't built yet.

### The flaw we hit

Argo deploys **manifests from every commit on main** but the **image only on a
tag**. A manifest change that needs a new image (the migration Job needs the
`migrate` profile) breaks prod as soon as it's pushed, before the release.

1. Workaround: pause auto-sync, push, release, resume.
2. Real fix: a separate deploy repo that the release job writes manifests **and**
   image tag into, in one commit. Then main never touches prod.

## Migrations as a gated rollout step

```
wave 0  Postgres, Services, NetworkPolicies, HTTPRoute
wave 1  Job yscord-migrate  (Sync hook)   ← must succeed
wave 2  Deployment yscord                 ← only then
```

1. **A Job** runs the same image with the `migrate` profile: no web server,
   migrate, exit 0 or non-zero. App pods run with `DB_MIGRATE=off` and refuse to
   start while migrations are pending.
2. **A hook, not a plain resource:** a Job's pod template is immutable.
   `hook-delete-policy: BeforeHookCreation` recreates it per sync and keeps the
   last one for `kubectl logs job/yscord-migrate`.
3. **Sync hook in a wave, not PreSync:** PreSync runs before everything, so on a
   fresh cluster Postgres wouldn't exist yet.
4. **A new pod label needs NetworkPolicy.** Under default-deny the Job's pod
   (`app: yscord-migrate`) can resolve `postgres` but can't connect: it needs its
   own egress policy and a place in Postgres' ingress.
5. **An unknown Spring profile is silently ignored.** The old image with
   `SPRING_PROFILES_ACTIVE=migrate` started the whole app inside the Job — a
   second writer that never exits.

### The runner

[resources/db/migrations/README.md](../src/main/resources/db/migrations/README.md) holds the rules.

1. Plain SQL files, applied in one transaction under `pg_advisory_xact_lock`:
   concurrent runners queue up, a failure rolls back everything.
2. SHA-256 per file; an edited applied migration logs a warning.
3. **Model-first:** change `PlayerTables.kt`, run
   `./gradlew generateMigration --name what_changed`, review the draft. The
   generator sees differences, not intent: a rename looks like DROP + ADD.
4. Never reference live table objects from a migration: the old V001 created
   V002's columns on fresh databases, so prod and fresh databases differed.
5. Down files are for local development. Production only goes forward.

### Tests that guard migrations

| Test | Catches |
|---|---|
| `SchemaInSyncTest` | model changed, migration forgotten (or the reverse) |
| `MigrationsOnDataTest` | migration that only works on empty tables |

The generator and the guard compare the model with a **fresh** database. Drift
between environments (prod had no defaults) only shows in a dump of the real one:

```fish
kubectl exec postgres-0 -- sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --schema-only'
```

### Expand / contract

Every migration must work with the previous and the next version of the code.
Merging columns A and B into C:

1. Release 1, expand: add C, backfill it from A and B, code writes all three and
   reads C.
2. Release 2, contract: drop A and B, once no pod of release 1 is left.

## Incident: v0.3.0

1. `004` added `muted BOOLEAN NOT NULL` without a default. Tests passed: their
   table is empty when migrations run. Prod has a row →
   `column "muted" contains null values`.
2. Effect: Job failed, sync failed, wave 2 never started, the site kept running
   0.2.0. The gate worked.
3. **Retry amplification:** Exposed (3 attempts) × Job (`backoffLimit: 2` → 3
   pods) × Argo (1 + 5 retries) = 54 runs of a migration that fails the same way
   every time. Retry transient errors in one layer only.
4. Action items: seeded migration test, `maxAttempts = 1` in the runner,
   explicit Argo retry, `004` fixed in place (never applied anywhere, so editing
   is allowed; "don't edit" means "don't edit applied").

## Diagnosis path

```fish
kubectl get pods -w                                   # what started, in what order
kubectl logs job/yscord-migrate | grep -iE "error|migrate"
kubectl describe job yscord-migrate                   # BackoffLimitExceeded, events
kubectl -n argocd get application yscord -o jsonpath='{.status.operationState.message}'
kubectl get deploy yscord -o jsonpath='{.spec.template.spec.containers[0].image}'
```
